# 阶段 1 输入契约

产品包不依赖 spike。`MeetingTranscriptSource` 的 `start/stop` 管理采集，`read(consumer_id, limit)` 读取本会议的持久化交付，`acknowledge(consumer_id, sequence)` 确认已持久化消费的连续前缀；读取本身不代表消费成功。真实 LLM 与基于行为文档的自主参与已在阶段 2.2 接入；consume --backend codex --watch 持续处理，固定截止日期测试规则独立使用 --backend rule。

每条 `Delivery` 有会议内采集顺序号和稳定交付 ID，类型为 `added/updated/conflict/status`。采集顺序是交付顺序；事件时间和发言时间用于上下文排序，未知时间不能补成当前时间。句子身份按会议隔离。没有句子 ID 的回退身份标记 `identity_degraded`，不能宣称同等去重可靠性。

`Caption` 保存句子键、可选句子/事件 ID、正文、说话人 ID/名称、语言、原始事件/起止时间、接收时间和采集模式。时间解析接受带时区的 RFC 3339（保留到纳秒）与起止字段中的整数毫秒；不把未知格式当成正确时间。字段名带 `_ms` 不代表实测值一定是数字。内容指纹涵盖正文、说话人、语言及起止时间，元数据更正也是变化。

飞书事件当前没有已核实的单调修订版本字段。`source_revision` 默认未知；适配器只有在有可核实版本契约时才能填入。不同内容的同一句没有可靠新旧依据时输出 `conflict`，保留已接受内容与候选，不静默丢候选，不通过事件时间猜测官方版本。可靠版本更新产生 `updated`；旧版重放不能覆盖新版。消费者按句子键替换上下文，冲突进入不完整状态，不能当作另一句追加。需要人工选择候选时通过显式操作解决，不能自动挑一个版本宣称正确。

采集模式为 `live/initial_replay/recovery_backfill`，重新投递另设 `replayed`。历史输入可以补上下文，正式问答不能直接触发对旧问题的回答。当前手动 consume 的固定测试规则处理所有未确认字幕（含回放/回补），用于验证消费至会中输出链路，不具备正式问答的新鲜度判断。首版假消费者的 `fresh_inputs` 仅演示分类，不能作为业务唤起策略；模型消费者检查原始发言结束/事件时间的新鲜度、参与策略及状态；未知时间只作上下文，回补模式本身不决定是否新鲜。恢复后的未确认输入必须可重放，消费者按交付 ID 幂等；处理成功后确认连续前缀，不跨过未处理记录。

状态为 `collecting/recovering/incomplete/action_required/stopped/ended`，带固定原因枚举、时间和可选疑似缺口区间。区间表示完整性风险，不等于测量出的漏句。空页只代表本次没有事件，不证明会议结束。状态变化也需持久化交付，不能只在终端显示。

状态和内容记录只有持久化成功才可读。下游消费确认与采集游标独立保存，消费者先持久化处理结果再确认。确认丢失导致重复投递，应由稳定 ID 消除重复。显式删除资料可终止重放能力，必须说明删除范围及不可恢复性；不能伪装成已消费。

`MeetingSource.start()` 在创建它的线程调用，内部启动独立采集线程；`read/acknowledge/state` 支持从下游线程调用，通过各线程自己的 SQLite 连接访问同一持久化记录。直接使用 `Store` 或持久化假消费者时，应在调用线程创建自己的实例，不共享同一 SQLite 连接。先停止 source，再关闭调用方存储。

采集模式描述输入获取路径，不单独证明发言的新旧：周期回扫也可能带来新近字幕。阶段 2 必须结合原始发言时间、接收时间、参与策略及源状态判断新鲜度，不能只按扫描模式丢弃问题；时间未知时也不能假定新鲜。假消费者的分类列表只是契约演示，未实现这一业务判断。
