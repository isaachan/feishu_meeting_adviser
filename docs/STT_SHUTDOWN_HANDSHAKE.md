# advisor / STT 停机握手修复方案

状态：待实施。范围为 advisor 与 stt-server 之间的流式识别停机收尾。

## 现象与问题

生产测试中，运维接口结束会议后，advisor 开始关闭 STT 连接；stt-server 处理 `stop` 后发送 `stopped` 时，连接已以 WebSocket 关闭码 1000 关闭，记录了 `ConnectionClosedOK` 堆栈。音频上行日志中的 `dropped=0` 不能证明停机瞬间的最后识别结果已交付并落库。

当前 `advisor/src/advisor/stt_client.py` 中后台 `_read()` 持续读取连接，而 `close()` 调用 `_wait_stopped()` 也读取同一个连接，存在并发 `recv()` 竞争和提前关闭的风险。需通过测试确认具体时序与影响；不能仅凭关闭码断言末尾字幕必然丢失或完全安全。

## 拟定方案

1. **单一接收者**：仅由后台 `_read()` 读取 WebSocket，不再由停机流程直接调用 `recv()`。
2. **最终结果和停止确认**：`_read()` 对 `final` 按现有回调处理，对 `stopped` 通知等待的停机流程，例如使用 `asyncio.Event` 或 future。确保按 STT 发出的顺序先处理最后的 `final`，再确认停止。
3. **有界停止**：`close()` 发送 `stop` 后等待停止确认，再关闭连接并清理接收任务。断线、发送失败、等待超时或任务取消均应有界清理并记录明确原因，不能无限阻塞。检查重复调用 `close()` 和尚未建立连接等边界。
4. **STT 正常关闭日志**：区分正常关闭码 1000 与异常断线；正常关闭不打印误导性的异常堆栈，异常关闭仍保留可诊断信息。连接提前关闭时依然释放识别会话与并发计数。
5. **会话排空语义**：核对 ingest、supervisor 和字幕落库路径，确保正常停止时最后 `final` 被处理后再视为 STT 收尾完成；对断线或超时明确可观察的失败行为，不把超时误当作已确认收到全部结果。

实现应兼容现有 STT 消息协议及本地、生产部署，不引入新的客户端参数。若实现发现需要改变冻结契约或会话排空语义，先更新相应契约并同步两端。

## 验收

- 模拟真实握手：STT 在 `stop` 后依次发送末尾 `final` 和 `stopped`；确认 advisor 处理末尾结果后才完成关闭，无并发 `recv()`。
- 覆盖没有末尾 `final`、多条 `final`、提前断线、发送失败、停止确认超时和重复关闭；确认资源释放且停机有界。
- 测试正常关闭不产生误导性堆栈，异常关闭仍能定位原因。
- 验证会议从 recording 到 draining、ended 的完整路径，检查末尾字幕落库；真实环境再次结束测试会议，检查 advisor 和 STT 日志。
- 涉及代码变更的 `advisor` 和 `stt-server` 按各自版本规则从 `0.1.0` 升至 `0.1.1`；分别运行相关测试，并更新生产部署版本。
