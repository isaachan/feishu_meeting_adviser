# 同一会议复用 OpenCode 会话：讨论记录

状态：**方向已对齐，待技术验证与方案设计；尚未实现**。本文记录现状、目标和需要解决的问题，不是已冻结的跨模块契约。当前架构与接口以 [ARCHITECTURE.md](ARCHITECTURE.md) 和 [推理身份扩展](CONTRACT_INFERENCE_IDENTITY.md) 为准。

## 1. 背景与目标

用户已明确：**同一场会议的多次模型判断应复用一个长期 OpenCode session**。这样后续判断可以利用同一会话中较早的对话、skill 加载和工具调用上下文，而不是每次完全独立执行。

OpenCode **进程**和 **session** 是不同概念。已对齐的是会议内复用同一个 session；是否每场会议独占一个长期进程，还是多个会议共享一个进程并各自使用独立 session，尚未决定。

## 2. 当前实现

现在每次判断由 advisor 生成会议快照并提交到 llm-gateway；gateway 为每次任务启动隔离的 OpenCode 进程、创建 session、提交请求，完成后删除 session 并清理进程。下一次判断重新创建，不能直接访问前一次 OpenCode 的对话、skill 和工具调用历史。

后续任务并非完全没有上下文：advisor 会重新提供保留的字幕、会议资料、待发送和近期已发送回复；gateway 可注入该会议的 NSDP 版本目录。但这些不是前一次 OpenCode 的完整会话历史。

## 3. 目标运行形态

```text
会议开始 → 创建或绑定 OpenCode session
  第 1 次判断 → 在该 session 中处理
  第 2 次判断 → 继续使用同一 session
  后续判断   → 按顺序继续使用同一 session
会议结束 → 排空任务并清理 session
```

advisor 继续负责会议状态、字幕、调度、结果时效和证据校验；gateway 负责通用的会议级 OpenCode session 生命周期。具体版本知识、风险判断等仍属于 skill 与工具，不放入 advisor。

复用 session 不等于模型永久、可靠地记住全部内容：历史仍受模型上下文上限和压缩策略影响。

## 4. 需要设计的问题

1. **生命周期与隔离**：明确会议和 OpenCode session 的绑定、创建时机、结束排空与残留清理；比较每会议独立进程和共享进程多 session 的资源、隔离、凭据及部署影响。不同会议及组织者的信息不能混用。
2. **每轮输入与状态权威**：首次如何提供会议资料和版本目录，后续如何传递新增字幕及状态变化，避免反复堆叠完整快照。advisor 仍是会议状态的权威来源，须决定哪些状态需要重新同步。
3. **并发和消息顺序**：同一会议的模型判断保持有序；上一轮执行时新字幕继续进入 advisor，下一轮如何合并待处理内容、取消与排队。结果返回后仍需重新校验字幕证据、时效和会议状态。
4. **上下文长度与压缩**：会议越长历史越大，需要验证 OpenCode 压缩、截断及其对会议资料、版本目录、关键讨论和工具结果的影响；不能假设所有历史永久保留。
5. **失败、重试与恢复**：区分消息未送达、已送达但未返回、工具已执行等情况；避免重试把同一字幕重复加入 session。验证 gateway 或 OpenCode 重启后能否定位并恢复原 session，不能恢复时如何重建。当前以查询工具为主；未来写操作还需处理重复执行。
6. **工具结果与数据新鲜度**：旧的版本查询结果可能过期；需规定何时重新查询，以及如何保持组织者身份和工具权限绑定。会议级 NSDP 目录的既有固定快照与冷启动权衡仍按当前架构执行，除非后续明确变更。
7. **契约和可观测性**：更新 advisor ↔ gateway 的会话、任务、取消、幂等及重启恢复契约；记录 session 绑定、任务状态、skill/工具调用和失败原因，并验证超时和会议结束清理。

## 5. 建议先做的技术验证

在实际版本的 OpenCode 上：

1. 创建一个 session，连续提交两轮判断，确认第二轮可利用第一轮上下文及工具结果。
2. 验证同一 session 的并发请求、取消、中断后的消息状态与安全重试。
3. 验证 OpenCode / gateway 重启后的 session 保存、查找与恢复能力；明确不可恢复的边界。
4. 以长会议模拟验证上下文增长、压缩行为、工具结果新鲜度与资源占用。
5. 基于验证结果选择进程隔离方案，设计契约、迁移计划和端到端测试，再开始实现。
