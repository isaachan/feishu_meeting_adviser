# Windows 飞书会议麦克风静音联动：参考实现分析

状态：开发前调研，供评审；本文描述参考代码的实际行为及接入当前项目的关注点，不代表 Windows 客户端已经实现。

## 1. 目标与范围

Windows 会参谋客户端共享现有 Mac GUI 主体，使用 Windows 平台适配层采集飞书会议声音和本机 mic。mic 应随飞书会议中小 A 的静音状态联动：静音时停止采集小 A 的 mic 音频，开麦时恢复；Mac 的静音检测暂不实现。远端声音仅采集飞书相关进程的输出。

本文的参考实现位于 [`studies/windows-gui/meeting-asr-subtitle/`](../studies/windows-gui/meeting-asr-subtitle/)（下称参考项目）。它是 Windows 本地字幕程序，不是本项目的 recorder；本次重点分析 mic 静音检测、门控及设备管理，而非移植本地 ASR。

## 2. 参考项目的整体链路

飞书进程模式启动两个独立通道：`remote` 采集飞书进程输出，`local` 使用默认输入设备采集 mic，并开启 `mute_gate`（`main.py` 的 `AppState._start_sessions_locked`）。未找到 mic 时只运行远端通道。

```text
飞书会议窗口 ── UI Automation 轮询 ──► FeishuMuteDetector 状态
                                                │
默认 mic ── PortAudio 回调 ──► 音频队列 ──► 静音门控 ──► VAD ──► 本地 ASR
飞书进程输出 ── 进程级环回 ───────────────────────────► 独立的远端识别通道
```

主要代码位置：

| 文件 | 相关职责 |
|---|---|
| `feishu_mute.py` | 通过 Windows UI Automation 查会议窗口、读取静音状态，防抖并保存快照。 |
| `asr_engine.py` 的 `RecognitionSession` | 启停检测器；消费 mic 音频块时依据状态决定是否送 VAD；状态变化时通知界面。 |
| `audio_capture.py` | 默认输入设备采集、设备枚举、按名称匹配、采样率协商和重采样。 |
| `main.py` 的 `AppState`、`mic_watch` | 创建双通道，每秒检查默认 mic 及设备变化，必要时只重建本地通道。 |

## 3. 如何检测飞书里的静音状态

### 3.1 查找会议窗口

`FeishuMuteDetector` 启动后台线程，在该线程初始化 UI Automation，以约 **0.3 秒**间隔轮询。`_meeting_windows()` 遍历桌面顶层窗口，要求标题含 `飞书会议`、`Feishu Meeting` 或 `Lark Meeting`，窗口尺寸非零；排除常见浏览器标题。能获取到进程名时，还要求进程名包含 `feishu` 或 `lark`；获取不到进程名时不会因此排除窗口。

这是基于桌面窗口及其无障碍控件树的检测，不是读取系统麦克风静音状态，也不调用飞书会议 API。最小化、窗口标题、飞书版本或语言变化都可能影响识别。

### 3.2 按优先级读取控件

检测器遍历找到的会议窗口，取第一个能识别的信号：

1. **悬浮工具栏**：查找类名 `MiniDialogMicrophoneButton`。
2. **参会人列表中自己的行**：查找有 mic 操作按钮的列表项，以 Windows 显示名匹配本人；环境变量 `FEISHU_SELF_NAME` 可覆盖显示名。
3. **视频小窗**：查找 `ParticipantViewMicrophoneButton` 或 `ParticipantMicrophoneIcon`。代码按控件类名和名称读取，未额外验证匹配到的小窗一定属于本人。
4. **小尺寸悬浮窗**：在宽不超过 800、高不超过 500 的会议窗口内，查找任意匹配名称的控件。
5. 均未识别则报告未知；未找到会议窗口还会报告 `in_meeting=false`。

按钮名称表达的是**点击后的动作**，因此判断要反过来：`打开麦克风` 表示当前已静音；`关闭麦克风` 表示当前已开麦。其他名称，包括只有“麦克风”的控件，视为未知。当前实现只识别上述中文按钮名称。

### 3.3 防抖、保持与状态快照

- 原始结果按 `(静音值, 信号来源)` 连续一致 **2 次轮询**才提交切换，正常情况下需要两个轮询周期。
- 暂时无法读到状态时，沿用最近一次原始已知结果最多 **8 秒**，来源标记为 `hold`；超过后标记未知。注意代码在防抖确认之前就更新“最近一次原始已知结果”，因此保持值不一定是上一次已提交的稳定值。
- 快照包括 `muted`、`known`、`source`、`detail`、`in_meeting` 和更新时间；调用方通过 `get_state()` 获取。启动失败、检测异常或没有可识别控件都可能导致未知。
- 检测依赖窗口可见性和 UI 结构，无法保证与实际静音瞬时同步；参考文档也注明不支持空格按住临时发言（PTT）。

## 4. 参考项目如何联动 mic

### 4.1 启动与数据流

本地 `RecognitionSession` 启动检测器，最多等待约 **1.5 秒**获取已知状态，再打开 mic 采集。`AudioCapture` 使用 `sounddevice.InputStream` 回调采集单声道音频，协商采样率、重采样到 16 kHz；回调把音频块放入有界队列，识别线程从队列取块并执行门控。

门控优先级（`_mute_allows_audio`）：

| 条件 | 参考项目行为 |
|---|---|
| `force_local_mic=true` | 强制放行，优先级最高。 |
| `follow_feishu_mute=false` | 放行，不跟随飞书静音。 |
| 已知静音 | 拦截该块，进入静音时重置本地 VAD。 |
| 已知开麦 | 放行该块，继续识别。 |
| 状态未知 | **放行**并提示未知。 |

默认跟随静音、默认不强制开麦。状态变化时向界面发状态消息，携带检测快照。

**重要区别：参考项目的“静音暂停”实际是丢弃进入识别的音频块，并非停止 PortAudio 流或释放设备。** 静音期间 mic 回调和队列仍可能接收到原始声音；门控是在出队后、进入 VAD 前检查当前状态，而非给每个采集块绑定采集时的状态。队列积压及切换时序因此值得后续设计和验证，不能直接等同于“静音期间未采集”。

### 4.2 会议窗口消失

在跟随开启且未强制开麦时，如果连续 **10 秒**未检测到会议窗口，本地会话停止，随后停止采集并释放 mic；远端继续。再次进会需要重新启动相应模式。这个计时在处理音频块时检查；开启强制开麦或关闭跟随时不执行该自动停止逻辑。窗口最小化也可能被误判为消失。

### 4.3 默认麦克风与热插拔

`mic_watch` 约每秒通过 `soundcard`/WASAPI 重新枚举，避免 PortAudio 设备列表陈旧；仅飞书进程模式且本地通道正在运行时自动处理：

- 系统默认 mic 变化稳定约 **2 秒**后，停止旧本地会话并切换到新默认设备；默认仍指向已消失的绑定设备时等待约 **5 秒**后停止本地通道。
- 枚举和默认值同时为空时暂不动作，避免枚举异常导致误停；枚举正常但没有默认设备时，等待约 2 秒后停止本地通道。
- 优先按名称在 PortAudio 列表中解析设备；找不到时重初始化 PortAudio 并重试。切换失败尝试恢复旧设备；远端会话不随本地切换而重启。
- 用锁串行化手动启停和自动切换，界面展示绑定设备、系统默认设备和状态；事件写入本地日志。
- 跟随的是 **Windows 系统默认输入**，飞书内部选择了不同 mic 但未改变系统默认时，参考实现无法检测。设备名称模糊匹配、蓝牙模式变化和枚举失败都可能影响切换；参考文档估计切换中断约 1～2 秒。

## 5. 接入当前 recorder 的差异与关注点

### 5.1 门控位置必须覆盖本地保存和上行

当前 `macos-gui/src/macos_gui/capture.py` 创建 `CaptureSession`，每源对应一个 `SourceUplink`。`recorder/src/recorder/audio/session.py` 的 writer 从源队列取帧后既分发给订阅者（GUI 再送上行），又写入本地 `<source>.wav`。

因此直接照搬参考项目在识别阶段丢弃的门控，或仅在上行前拦截，不能满足本项目的目标：静音期间真实 mic 数据仍可能已被采集或写入本地。Windows 适配需要在音频进入保存和上行的共同路径之前落实门控，并处理启动、状态切换、回调在途和缓冲中的音频。需要区分“停止设备采集”与“设备继续采集但丢弃数据”；用户要求的是前者，参考项目本身实现的是后者。

当前 `MicSource.pause()` / `resume()` 通过停止 / 启动 PortAudio stream 实现暂停和恢复，并产生 `gap_begin` / `gap_end` 事件，可作为研究入口；它目前是手动开关，并未接飞书检测。接入前仍需验证线程并发、切换期间残留数据、设备异常和恢复行为，不能假定现有实现已完整满足目标。

### 5.2 流协议与源生命周期

- [`CONTRACT_RECORDER_STREAM.md`](CONTRACT_RECORDER_STREAM.md) 要求 loopback 与 mic 各自连接、序列独立；mic 需要明确启用。当前 GUI 根据服务端返回的 `recorder_command_args.mic` 是否创建 mic 源，因此后续要确保用户启用 mic 的入口与服务端参数相衔接。
- 契约 §2.3 定义 `gap` 作为 MuteGate 切换的断句边界；§2.2 还要求静音发送零值帧以保持时间轴。如何在停止真实 mic 采集的同时满足时间轴、连接保活、缺口事件和重连语义，需要结合现有 uplink 实现设计并验证，不能简单照搬参考项目的 ASR 重置。
- 设备切换应维持本地源的时间线和连接语义，不因重建设备而影响远端采集；要验证切换失败、无设备及恢复时的行为。

### 5.3 状态未知与识别限制

参考项目的未知状态默认放行，是其本地字幕场景的**既有行为**。会参谋已对齐：**状态未知时暂停 mic 并提示，明确检测到开麦后自动恢复**。启动尚未检测到状态、检测线程异常、窗口消失和长时间读不到状态，都不能把“未知”当作“已确认开麦”。

参考实现依赖飞书桌面会议窗口、中文控件名称和 UI Automation，且存在轮询延迟及误判可能。后续 Windows 真机测试应覆盖飞书主窗口/悬浮窗/最小化、静音与开麦切换、设备插拔、检测不可用及会中退出；检查 mic 本地 WAV 与上行的实际内容，同时确认远端仅来自飞书且不受 mic 变化影响。

## 6. 本次对照结论

参考项目提供了可移植的 **Windows UI Automation 多信号检测、防抖/保持、设备监听与切换思路**；但它的 mic 门控发生在采集之后，且未知状态默认放行。当前项目需将检测结果接到采集源和 recorder 生命周期上，才能实现已对齐的静音停止采集目标。当前阶段只完成调研文档，Windows 客户端及真机验证留待评审后进行。
