# 产品需求 · v0.4（草案）

状态：v0.4 为业务目标草案，尚未实现/冻结；现行实现仍以 [STATE_MACHINES](STATE_MACHINES.md) 等契约为准。人物与场景是本文的核心；目标状态机和角色关系见 [SERVICE_STATE_MACHINES_V2](SERVICE_STATE_MACHINES_V2.md)、[DOMAIN_MODEL_V2](DOMAIN_MODEL_V2.md)。
修订：v0.2 重写 S1 为"bot 指令驱动"流程（OAuth 上云、命令下发、自动 consume）；v0.3 评审修订：删除暂停/恢复辅助、订阅 revoked 定为终态、draining/ended 拒新订阅、命令模板修正（mic 默认关、明文 ws）、授权链接统一经 advisor 下发、材料来源定为建会时从日历事件描述自动带出；v0.4 业务调整：新增小C与 S6、区分飞书角色与 advisor session owner，增加自动 paused、同会唯一/用户单会归属、订阅者取消后重新申请。具体实现与 API 变更仍须另行评审。

## 1. 产品定位

会参谋为一场飞书会议提供实时辅助（听会 → 理解 → 判断是否需要补充或回答）。**小A（会议组织者）和小C（管理员授权的测试用 supervisor）是飞书会议语境中的身份；advisor session owner 是会参谋语境中的权限归属，合资格的小A或小C先成功建会者担任。**会参谋的订阅审批、默认回答接收、查询凭据归该 owner；已批准的订阅者只接收后续回答，不获取完整字幕或录音。录音由采集设备本地留存，不因上述权限归属自动上传。

## 2. Personas

### 小A —— 会议组织者（主持人）

- 有飞书账号；目标会议在她的日历上，且**她是该日历事件的组织者**（准入校验条件）。
- laptop（Mac 先行，Windows 跟进）上有飞书客户端，通过 recorder 命令或 GUI 采集上行。recorder **不保存用户 OAuth 凭据**，仅持该会话流令牌。
- 首次使用时在飞书里点一次授权链接完成 OAuth（凭据保存在云端，此后自动刷新，免打扰）。
- A 可通过**与 bot 私聊**请求入会；若先成功建会，成为该场 advisor session owner，随后可结束、审批/撤销订阅，默认接收回答；采集可通过 recorder 或 GUI 进行。
- 若该场会话已由 C 先创建，A 仍是飞书会议组织者，**但不是** advisor session owner：不能再为该场创建第二个 session，也不能接管采集/控制或订阅 C 的会参谋回答。
- 期待：自己作为 owner 时，开会像带了一个不出声的参谋，该提醒的提醒、该回答的回答，都发到飞书私聊里。

### 小B —— 普通参会者

- **只装飞书，什么都不装**，不部署任何东西。
- 通过与"会参谋 bot"单聊表达诉求；收到的内容由该场 **advisor session owner（A 或 C）** 审批决定。订阅申请提交即暂占一个会话名额，只有批准后的新回答会送达。
- 可以退订，之后重新申请；每次重新申请均用新编号、重新审批，不回溯此前的回答。不能同时在另一个未结束的 advisor session 里作为订阅者或 owner。
- 明确不能做的事：驱动 AI（提问、改变模型行为）、获取授权范围之外的内容（如完整字幕、录音）。

### 小C —— 经 admin 授权的测试用 supervisor

- 是**飞书会议语境**中的受邀参会者或日历组织者；小C由 admin 在名单中以 `kai.han` 一类账号标识配置，服务端需解析并绑定稳定的飞书身份。名单资格本身不足以入会，仍须核实 C 在**目标场次的日历邀请名单**（直接受邀或为受邀群组成员；或本人为组织者）；不能仅凭会议号创建 session。不要求 C 在建会瞬间已经进入实时会议。
- 可像小A一样对 bot 发入会指令；持有自己所需的飞书授权与查询凭据，在自己的 laptop 上通过 GUI/recorder 采集上传，目的是便于会参谋开发者测试。
- 若 C 先成功创建该场会参谋 session，C 就是该 session 的**唯一 owner**：审批/撤销订阅、接收默认回答、使用 C 自己的 NSDP/Jira 等查询凭据；C 的离会/回会驱动该 session 的 `paused/running`。即使 A 随后加入飞书会议，owner 也不自动转移给 A。
- C 若已在另一未结束的 advisor session 中作为订阅者（申请待审批也算占位）或 owner，就不能再发起新的 session；退出订阅或旧 session ended 后才释放相应归属。

## 3. Scenarios

### S1 · 小A 启动一场会议（含首次授权）

前提："会参谋"是已配置好的企业自建应用（bot 能力已开通）。

1. **指令**：小A 在飞书对会参谋 bot 说："你要入到这个会中，会议 id 是 123456789"（或直接发一个 `vc.feishu.cn/j/` 会议链接）。
2. **鉴权（仅首次或凭据失效时）**：bot 经 advisor 查云端是否已有小A 的有效授权；没有则 advisor 返回授权链接、由 bot 转发小A，小A 在浏览器（电脑/手机均可，需能访问部署网络）完成飞书 OAuth；user access token 保存到**云端**（按小A 身份隔离），此后 advisor 自动刷新。**小A 全程不接触 token 明文。**
3. **校验**：bot 背后的 advisor 用小A 的授权读取飞书日历，核对会议存在、小A 是该日历事件的**组织者**、当前在会议时间窗内，以及小A 尚未归属另一未结束 session。若该场已有**自己**创建的 session，幂等返回原 session；已由 C 建会则告知此场已有 owner，不重新建会。任一准入条件不满足，bot 明确告知原因。
4. **建会与命令下发**：校验通过 → advisor 创建会话，phase=`running`（含义是会参谋已就绪、允许采集，不依赖飞书会议是否真正开始；顺带把校验时读到的**会议事件描述**存为背景材料；描述为空则无材料，不阻塞）并**自动启动 consume**。小A成为 session owner，bot 把采集器启动命令发给小A，形如：

   ```
   recorder real --session <会话id> --event '<cal>/<evt>' \
     --url ws://<server>/<ingest> --token <流令牌> [--mic]
   ```

   命令中含云端分配的会话 id、日历事件 id、上行地址与**短期流令牌**（仅绑定本会话）；`--mic` 为本机麦克风的显式开关，**仅在小A 明确选择开启麦克风时**才出现在命令中（默认不出现）。
5. **执行**：小A 在 laptop 终端粘贴执行命令，采集开始：远端声音（系统播放回路）默认开启；本机麦克风默认**关闭**（隐私优先：小A 在飞书静音期间不该被录的话，不进链路）。整场原始音频本地留存（排障/重转写用），不上传。laptop 不保存任何用户凭据。

验收口径：未授权（拒绝授权链接）、非组织者、超时间窗、会议不存在，以及同场已由 C 建会/自己已占另一未结束 session，bot 均拒绝并说明原因；同场并发入会只由先成功者持有该场唯一 session；下发的命令文本中**不得出现 user access token**。

备注：v1 命令为复制粘贴执行；"一键启动"（本地守护进程 + IM 内链接唤起）列为后续增强。

### S2 · 会中辅助（advisor session owner 的主链路）

1. 采集器把音频持续上行到云端 advisor（远端回路常开；本机麦克风开启时加一路；**每路一条独立连接**，每路约 32 KB/s，流令牌鉴权）。
2. 云端转写为字幕 → 进入该会议的会话上下文（字幕 + 建会时带出的会议描述材料）→ 模型判断是否需要发言。
3. 需要时，会参谋 bot 把回答（LLM reply）以飞书私聊发给**本场 advisor session owner（A 或 C）**。

验收口径：说完一句被回答的话 → 本场 owner 飞书收到回答，全链路 P95 时延预算 ≤ 20 秒（由旧"15 秒字幕 + 5 秒 LLM"拆分预算合计而来，待端到端实测修订）。

### S3 · 参会者订阅（小B + 本场 owner 审批）★ 核心新场景

前置：小B 在飞书里能找到会参谋 bot（应用可被发现/可添加）。

1. **申请**：小B 给 bot 发消息："你好，我想收到会议 123456789 的信息"。
2. **校验**：bot 解析会议号，在云端按**会议号 + 会议时区 + 当地日期 + 当日场次**定位目标场次；若同号存在多个候选场次，必须先消歧，不误订另一场。目标 session 处于 `running` 或 `paused`（**已定 2026-11-16：paused 受理**）且小B未占另一未结束 session → 生成订阅申请（状态 `requested`，申请即占位）；未命中或已进入 draining/ended → 告知该场不可订阅。审批申请需有超时，到期释放占位（`requested` 申请人可自行撤回，**已定**）。
3. **审批**：bot 给该 session owner（小A或小C）发私聊："小B 请求接收会议《标题》的会参谋回答，回复『同意 #rN』或『拒绝 #rN』"。
4. **owner 回复**：
   - 同意 → 订阅置 `approved`，bot 回执双方；**从下一回答起**，小B 与本场 owner 同时收到 LLM reply。
   - 拒绝 → 订阅置 `denied`，回执小B。
5. **撤销或主动退订**：owner 对 bot 撤销小B订阅，或小B主动取消 → 即时停止该收件人的新回答与尚未发出的 pending 回答。本人取消后可向同场重新申请（新编号、重新审批）；owner 撤销后的再次申请**允许**（**已定 2026-11-16**，同样新编号重新审批），旧申请行始终保留历史。
6. **重复申请幂等与超时**：已 `approved` 再申请只提示当前状态；`denied` 或本人取消后重新申请创建新编号、新审批；`requested` 长期不审批则超时过期、释放唯一会话占位，再申请亦走新编号/新审批。

边界（显式约束）：

- **仅前向**：批准只对之后新产生的回答生效，不回溯历史回答。
- 小B 收到的是**会参谋的回答**，不是完整字幕或录音。
- 小B 的任何消息都不进入模型上下文、不触发模型调用。
- 审批请求的 **IM 通知** 不承诺可靠投递（bot 离线可能漏发给 owner），但 advisor 中已创建的 `requested` 申请和占位不会随通知丢失；申请到期自动释放占位，小B可按新申请重发。已批准的回答分发走 outbox。

### S4 · 会中问答与控制（advisor session owner）

本场 owner（小A或小C）对 bot 的指令集（全部走私聊文本，规则解析、不进 LLM）：

- `入会 <9位会议号 | 会议链接>`（小A 见 S1，小C 见 S6）
- `结束会议 [会议号]`（停止辅助，云端有界排空收尾；一个用户只能归属一个未结束 session，误结束不可逆）
- `同意 #rN` / `拒绝 #rN`（审批，#rN 为 advisor 全局分配的订阅请求编号）
- `撤销订阅 <小B> <会议号>`
- `状态`（列出全部进行中会话的采集/模型/订阅概况）

### S5 · 收尾与异常

- **正常收尾**：飞书会议结束（自动感知能力待验证）或本场 owner 对 bot 说「结束会议」→ session 进 `draining`、拒新音频/订阅；已有源、模型任务、回答正常完成后置 `ended`。`draining` 必须有持久化总截止时间：到期仍未完成则记录丢失/失败，取消确定未发送的回答，结果不明的发送记 `uncertain`，随后 `ended`；不能因 bot/STT/gateway 下线无限停留。误操作提前结束，接受该场无法再建第二个 session。
- **owner 离会/回会**：只有 advisor session owner 的实际离会触发 `running → paused`，同一 owner 回会触发 `paused → running`；小A若不是该 session owner，其进出不触发迁移。owner 在会状态如何查询见 [TODO](../TODO.md) T12；查询失败不能推定离会。暂停时在途字幕/模型任务/待发回答**立即作废**（**已定 2026-11-16**；恢复后从新字幕重新判断，已送达内容不追回），不得无限等待。
- **GUI/recorder 停录与空闲**：用户停录只改变客户端 `recording → not_recording`，不等于 session `paused`。在 session 仍 `running` 且距离最后真实音频不足 900 秒时，可重新选择同一 session 开始采集；`running/paused` 连续 900 秒无上行则进 `draining`，不再允许重开。首次计时从建会起，心跳不算音频。
- **网络断线**：采集器本地缓冲、恢复后重传；断线期间未完结的语句丢失（与旧 STT 契约语义一致）。云端对已收到的输入照常处理。
- **laptop 合盖/退出**：等同断线且不自动恢复；云端继续处理已收到的输入；若 900 秒仍无音频则进入 draining 并有界排空。
- **云端不可用**：采集器本地持续留存音频（证据在手），字幕丢失不补（v1 不做事后重转写，列为后续增强）。
- **授权失效**：owner 的 refresh token 过期时，bot 在下次需要校验前重新发授权链接，由该 owner 授权后续接原意图；小C 使用自己的凭据，不借用小A 的授权。

### S6 · 小C 以受邀参会者身份启动会参谋（开发测试场景）

1. **管理员配置与本人准备**：admin 将 `kai.han` 一类账号加入小C名单，并解析到唯一飞书 `open_id`。小C登录飞书、完成自己的飞书 OAuth 及入会所需的 NSDP/Jira 凭据准备；GUI/recorder 准备采集，但这些凭据不下发给采集端。小C是这场会议的受邀参会者，**不是日历组织者**。
2. **发起与准入**：小C对 bot 发「入会 <会议号/链接>」。advisor 核实名单资格、**该场日历邀请名单有小C**（直接受邀或为受邀群组成员）、入会时间窗及必要凭据；再按会议号 + 权威会议时区 + 当地日期 + 当日场次解析唯一会议实例，同时检查该实例一生没有第二个 session、小C当前没有归属其他未结束 session。仅凭知道会议号或 admin 名单资格都不足以准入。
3. **先到先得**：如果小C先成功建会，小C成为**唯一 advisor session owner**，session 立即 `running`＝会参谋已就绪/可接收音频，**不依赖飞书会议是否已开始**。bot 将采集参数交给小C；小C可在 GUI 选择该会话开始录音/上传。若小A先建会，小C不能再创建这场的第二个 session；若小C已申请订阅另一未结束 session（包括待审批），也不能再成为本场 owner。
4. **权利与通知**：C 建会后，由 C 审批/撤销小B的订阅，C 默认收回答；模型查询只使用 C 自己的身份和查询凭据。小A后来进入会议仍是飞书组织者，但不会自动变成会参谋 owner，不能订阅或接手 C 的 session，也不会因为小A离会而使该 session 暂停。
5. **离会、停录、恢复**：小C实际离开飞书会议 → 其 session 进入 `paused`，小C回来 → 恢复 `running`（自动在会检测能力待验证）。小C手动点「暂停采集」仅停止本地上行，不改变 advisor phase；只要还在 `running` 且无音频不足 900 秒，可再选同一个 session 点「开始采集」。超过 900 秒无音频或小C主动结束后进入 `draining`，排空有最晚完成时间，到期记录未完成项并进入 `ended`；结束不可逆。

**验收口径**：小C受邀但非组织者也能建会；不在 C 名单或不在该场邀请名单则拒绝；A/C 并发只建一个 session，C 成为 owner 后 A 不能接管；C 的凭据、默认回答和订阅审批与 A 隔离；C 离会/回会影响自己的 session，A 的进出不影响；同一用户已占另一未结束 session 时拒绝再次占位；同一 9 位号跨天或同日不同场次可分别建会。

## 4. 范围与非目标

**目标范围（v0.4 业务草案，非现行 v1 已实现能力）**：S1–S6；单云端部署（内网/受信网络）；多个用户共用部署、按用户隔离；**每场会议实例至多一个 advisor session**，每名用户同一时刻至多归属一个未结束 session（owner 或订阅者，申请待审批也算占位）。所有重要操作必须有有限超时及到期动作，具体数值除无音频 900 秒外待实施时确定。

**非目标（v0.4 业务草案）**：

- 小B 驱动模型（任何形式的问答）。
- 批准后回溯历史回答。
- 群聊内 @bot 问答（旧 chatbot demo 能力，不带入）。
- 用户手动把 advisor session 切到 `paused`（该状态仅由 owner 实际离会触发）；GUI 的「暂停采集」只控制本地录音上行。
- 即时会议（无日历事件）的采集与订阅。
- 多设备对同一会议双录、字幕合并。
- 公网匿名注册开放（部署受信边界内运营）。
- 录音/字幕的会后产品（妙记类能力）。
- 从 IM 链接一键唤起本地采集器（GUI 中手动选择会话并点「开始采集」不属于此项）。
