# 字幕获取约 30 秒延迟调研（TODO 3.5）

调研日期：2026-10-19。数据来源：本机 `data/source.sqlite3`（`deliveries` 表，仅提取时间字段，未读取正文/身份）与 `data/diagnostics/*.jsonl`，覆盖 2026-10-13 至 10-18 共 25 场授权测试会议、约 570 条 live 字幕。官方契约依据公开文档；低延迟通道依据用户提供的《飞书智能体入会 · 接入手册（对外版）》（docx，对应在线文档需登录，未提交仓库）。

## 一、结论

实测约 30 秒延迟是**飞书侧持续的暴露延迟**，不是一次性固定缓冲，也不是本产品的调用方式（轮询起点、游标/时间过滤、首读范围）问题。

1. **客户端已排除**：产品以 `poll_seconds=0.7` 轮询，诊断显示实际分页间隔中位 1.03 秒（含请求耗时）；"每秒一句"测试会话中，首句被取到前程序已连续空轮询 16 次且查询窗口早已覆盖该句的 `event_time`。扫描窗口（首读回看 600s、重叠 120s、60s 周期回扫）不影响可见性。
2. **延迟在服务端**：`event_time − end_time`（发言结束）中位为 −3～0 秒，即事件时间戳≈发言时刻；而 `received_at − event_time` 全场次中位 **31 秒、P95 40.3 秒、max 51.9 秒**（各场中位 28–37 秒）。事件在发生后约 30 秒才可被 `bots/events` 查到。
3. **"一次性缓冲"是错觉**：以恒定语速说话 + 恒定 ~30s 管道延迟，首句在第 31 秒出现后输出速率等于说话速率（每句都迟到约 30 秒），主观即"不再有额外延迟"。诊断中每页 `new_end_receive_seconds` 全程稳定在 22–35 秒可证每句都延迟，而非仅首句。
4. **延迟量随场次波动**：阶段 0 曾记录中位约 15 秒（见 [STAGE0_FINDINGS](STAGE0_FINDINGS.md)），本次 25 场稳定在 ~31 秒，说明是波动的服务端暴露延迟而非固定常量。
5. 附带核对：collect 重启后的 `initial_replay` 年龄 56–84 秒属停机积压重放，预期行为；API 频率 100 次/分钟，当前 ~1 次/秒轮询在限内。

**对 20 秒目标的影响**：纯拉取路径下字幕单项 P95 已约 40 秒，"15 秒字幕 + 5 秒 LLM"的预算不可达；需改用下述推送通道或重新基线。

## 二、其他字幕获取通道调查（公开文档 + 手册）

| 通道 | 类型 | 有无字幕 | 状态与备注 |
|---|---|---|---|
| `GET /vc/v1/bots/events` | 拉取 | ✅ `transcript_received` | 唯一会中字幕拉取来源；用户/应用身份均可（旁听模式全量开放）；~30s 暴露延迟；灰度能力，官方文档明示联系技术支持；依赖主持人开启 AI 汇总（错误码 120002） |
| `vc.bot.meeting_activity_v1` 等推送 | 推送 | ✅ 字幕/聊天/参会人/共享 | **手册披露：字幕等高频事件按 5 秒 / 100 条聚合下发**；随独立入会早鸟灰度开放；items 结构与拉取路径完全一致，外层多包 `meeting_activity_items` |
| `GetBotRealtimeEndpoint`（WebSocket） | 推送接收 | — | 仅在手册排查清单出现（"WebSocket 地址过期重新获取"）；公开文档页存在但非公开（403 This document is not public） |
| `vc.meeting.*_v1` 生命周期推送 | 推送 | ❌ | 只有开始/结束/进出/录制等；且仅 Open API 预约的会议产生推送 |
| `meeting-recording/*` 录制 API | 会后 | ❌ | 录制文件，需会议结束且录制完成 |
| 妙记（Minutes） | — | ❌ | CN 开放平台无公开 API |

VC 官方开发指南口径：事件订阅提供 Webhook 与 RTM 两种方式，"对实时性要求较高的场景推荐使用 RTM"——推送通道技术存在，字幕事件随早鸟灰度开放订阅。

## 三、手册其他相关要点

- 三种能力按开放程度递进：旁听模式（全量开放，用户 OAuth 轮询，无机器人入会）、独立入会（早鸟灰度，即本产品现行路径 + 事件推送）、语音互动（小范围共创申请，关联 TODO 0.9）。
- 每场会议需 owner 在安全设置开启**「允许智能体入会」**；找不到该选项先开 AI 总结（关联 TODO 3.4）。设置一次三种能力共用。
- 独立入会需订阅三个事件：`vc.bot.meeting_invited_v1`、`vc.bot.meeting_ended_v1`、`vc.bot.meeting_activity_v1`；手册强调事件字段名必须严格对齐，拼错收不到。
- `BotJoinMeeting` 必传 `join_type=1`：本产品已传（client.py join payload），无缺口。
- 字幕 `user_type` 可能为声纹检测类型（100/101/102），解析需兼容。
- 旁听模式同为 `bots/events` 拉取，预计同样存在 ~30s 延迟，未单独实测。

## 四、建议路径（未实施）

1. 加入早鸟体验群，确认应用可订阅 `vc.bot.*` 三事件及推送接收方式（Webhook / RTM / `GetBotRealtimeEndpoint` WebSocket）。
2. 订阅后实测推送时延（对照本文 ~31s 拉取基线）；预期 ≈ ASR 出句 + 5 秒聚合。
3. 若达标，输入源改造为**推送为主、`bots/events` 拉取补偿/对账**（手册亦标注拉取用途为"补偿 / 断线重连"）；推送 items 与现有 collector 解析兼容，需新增外层 `meeting_activity_items` 解包与推送接收端，复用现有持久化幂等管道。
