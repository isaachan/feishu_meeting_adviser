# 旁听模式结论：v3 冻结，继续走 v2

决策日期：2026-10-22。本文件记录 v3（旁听模式）停止推进的结论与依据，供后续查阅；代码保留存档，不再开发。

## 一、结论

**旁听模式不再继续推进，v3 冻结。会中输入源继续走 v2（应用身份入会 + 官方会中字幕）。**

原因一句话：旁听模式与 v2 使用**同一条字幕拉取通道**（`GET /open-apis/vc/v1/bots/events`），该通道存在 ~25–40 秒的服务端暴露延迟，客户端无法优化；产品的 20 秒预算（约 15 秒字幕 + 5 秒 LLM）在此通道上不可达，而旁听模式没有低延迟替代路径。

## 二、依据

### 1. 真机验证：链路本身是通的

2026-10-22 真实会议验收：`login`（用户 OAuth，scope `vc:meeting.meetingevent:read`）→ `meetings`（GetUserActiveMeeting 正确发现会议）→ `listen`（page_token 增量轮询）全链路跑通，字幕成功接收并入库（含延迟统计）。**冻结不是因为功能不可用，而是通道能力上限不满足产品要求。**

### 2. 延迟实测与 v2 调研相互印证

- v3 真机实测：从发言结束（`end_time_ms`）到本机收到字幕约 **25 秒**，落在 v2 调研的波动带内。
- v2 调研（[TRANSCRIPT_LATENCY_INVESTIGATION](../../v2/docs/TRANSCRIPT_LATENCY_INVESTIGATION.md)，25 场会议、约 570 句）：该 API 的事件在发言结束后中位 **31 秒**、P95 **40.3 秒**才可查询到；即便每秒轮询、查询窗口早已覆盖该句也无改善，确认为服务端暴露延迟，非调用方式问题。
- v2 与 v3 调用同一 ListMeetingEvents 接口，仅鉴权身份不同（Tenant Token vs User Token），延迟结论直接迁移。
- v3 已内置 `caption_latency_seconds`（最近 200 句 median/p95/max，`status` 可查），实测数据与上述结论一致。

### 3. 旁听模式的能力边界决定了没有优化空间

- 手册明确旁听模式「**不支持实时推送（需轮询拉取）**」；轮询侧 v3 已接近最优（~1 秒间隔，API 限频 100 次/分钟），剩余优化空间不足 1 秒。
- 手册披露的低延迟通道是「三、独立入会」的事件推送（`vc.bot.meeting_activity_v1`，字幕按 5 秒/100 条聚合下发，预期 ≈ ASR 出句 + 5 秒），**即 v2 所在的独立入会路线**。低延迟目标与旁听模式互斥。
- 旁听模式的差异化优势（无机器人入会、其他参会者无感知、用户身份授权）对本产品不构成决定性价值：产品硬约束是低延迟会中输入，且会中聊天/参会人事件在 v2 的推送通道中同样提供（items 结构与拉取完全一致）。

### 4. 对 20 秒目标的影响

纯拉取路径下字幕单项 P95 约 40 秒，「15 秒字幕 + 5 秒 LLM」预算不可达。该判断与 v2 调研结论一致；达成 20 秒目标的可行路径是 v2 侧接入事件推送（v2 调研 §四建议：推送为主、拉取补偿/对账）。

## 三、v3 完成度（存档说明）

| 项 | 状态 |
|:---|:---|
| 实现 | 完整：OAuth（PKCE+刷新轮换）、GetUserActiveMeeting 会议发现（免配置会议号）、ListMeetingEvents page_token 增量轮询、幂等去重存储、权限错误终态策略、延迟统计 |
| 测试 | 69 个合成数据测试全部通过（不调真实会议） |
| 真机验收 | 链路与数据正确性已验证；延迟指标不达标（即本结论的直接原因） |
| 未启动 | M4（消费对接：IM 推送 / LLM 问答），随冻结取消 |

`docs/SPECTATOR_PLAN.md` 中的里程碑 M4 及后续项不再执行；本文与该计划冲突时以本文为准。

## 四、后续路线

1. 会中输入源回归 v2 单一路线；v2 现有采集（应用身份入会 + 轮询）继续使用。
2. 低延迟改进按 v2 调研建议推进：加入早鸟体验群、订阅 `vc.bot.meeting_activity_v1` 等推送事件、实测推送时延；达标后将输入源改造为推送为主、`bots/events` 拉取补偿。
3. 若未来旁听模式开放推送或拉取延迟显著改善，可基于本文与既有代码（`v3/src/feishu_spectator/`，解析/存储管道与推送 items 结构兼容）重新评估。
